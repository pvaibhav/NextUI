## Goal

Replace the single on/off white-point gain correction with a 1D-LUT based
"Colour correction" system: per-model bundled `.cube` files plus the existing
R/G/B gains as a "Custom" mode, selectable from the Display settings menu.
Work happens on a new branch cut from `h700`.

## Success Criteria

- Display menu shows "Colour correction" with exactly three options:
  Off, On, Custom.
- "On" applies the bundled device-specific `.cube` (3x1D LUT) through the
  existing 256-entry kernel gamma table path.
- "Custom" applies the current R/G/B linear-gain behaviour with per-model
  default gains preserved.
- Selection persists across reboots; boot/sync paths apply the stored mode.
- Malformed, missing, or non-256-entry files never leave the display in a
  broken state (rejected before touching the kernel).

## Context And Current Facts

- `workspace/all/common/displaycal.c` builds a fixed 256-entry gamma table and
  pushes it via `/dev/disp` ioctls (`0x10b` set table, `0x10c`/`0x10d`
  enable/disable). Gains are applied in linear light with an sRGB round-trip
  (`srgb_to_linear` / `linear_to_srgb`). Identity table + disable is the off
  path.
- `workspace/all/common/displaycal.h` holds per-model default gains
  (`DisplayCalDefaults_*`, `DisplayCal_getDefaultSettings`) covering TrimUI
  (Brick, SmartPro, BrickPro) and the Anbernic H700 family.
- `workspace/h700/libmsettings/msettings.c` persists `displaycal_enabled`
  (bool) + 3 gains in `SettingsV1`. Its loader is strict: anything that is not
  exactly a V1 record resets to defaults (no migration chain). `SetRawDisplayCal`
  is the single hardware choke point; `InitSettings` and
  `workspace/all/syncsettings/syncsettings.c` re-apply at boot/sync.
- `workspace/tg5040/libmsettings/msettings.c` is at `SettingsV11` with a
  `peekVersion` migration chain; desktop and tg5050 share the same
  Get/Set DisplayCal API shape.
- `workspace/all/settings/settings.cpp` Display menu: "White point correction"
  on/off picker plus always-visible Red/Green/Blue gain sliders
  (`DISPLAYCAL_GAIN_MIN/MAX`). `hasDisplayCal()` is true for tg5040 and h700.
  Static multi-option pickers have precedent (e.g. Default view, on/off
  toggles).
- Bundled read-only data files have precedent in
  `workspace/all/common/palette.c` (`RES_PATH/palettes` built-ins). On h700,
  `SDCARD_PATH` is `/mnt/SDCARD` (`workspace/h700/platform/platform.h`);
  skeleton ships SD content via `skeleton/SYSTEM/res`.
- Build wiring: `workspace/h700/libmsettings/makefile` compiles
  `displaycal.c` into `libmsettings.so`; `workspace/all/settings/makefile`
  lists each `../common/*.c` explicitly, so a new shared source file must be
  registered in both places (and the tg5040/desktop/tg5050 libmsettings
  makefiles that mirror h700's).
- Working tree is clean on `h700`.
- Supplied measured files (RG40XXV, RGSP, RG34XXSP, BrickPro, 2026-09-07):
  each is `#` comments + `TITLE` + `LUT_1D_SIZE 256` + identity
  `DOMAIN_MIN`/`DOMAIN_MAX` + exactly 256 `R G B` float rows in [0,1].
  Confirms the D1 format assumptions for the bundled path. Files will be
  stored lowercase matching the `DEVICE` env var (`rg40xxv.cube`, ...), so
  step 3 resolves them by direct path concat.

## Constraints And Non-goals

- Kernel exposes only a 256-entry 1D gamma table per channel; full 3D
  correction is out of scope. `.cube` files containing only a 3D LUT
  (`LUT_3D_SIZE`) are skipped, not applied.
- Loading user calibrations from the SD card is explicitly out of scope
  (dropped as too complex). Only bundled per-model files are supported.
- The `.cube` 1D layout could not be checked against the authoritative spec
  in-session (no direct network access; both fetch attempts failed), but the
  four supplied real calibration files confirm the expected layout
  (`TITLE`, `LUT_1D_SIZE 256`, `DOMAIN_MIN/MAX`, 256 `R G B` rows), so the
  parser requirements are now grounded in real data. The harness must still
  validate rejection of unexpected variants.
- No changes to the ioctl protocol, brightness/colortemp/contrast pipeline, or
  unrelated settings.
- Bundled per-model `.cube` files themselves are user-supplied measured
  data, not generated by this work; the code must ship complete with whatever
  set exists (possibly empty). Models without a bundled file use the
  Custom-gains fallback.

## Key Decisions

- D1: Parse `.cube` in shared `displaycal.c`, 1D-only: accept `LUT_1D_SIZE N`
  files (conditional: `TITLE`, `#` comments, `DOMAIN_MIN/MAX`,
  N lines of `R G B` floats), skip `LUT_3D_SIZE`-only files. Rationale:
  single parser serves all platforms; matches existing shared-file
  architecture. Alternative rejected: per-platform parsing (duplication).
- D2: Require exactly `LUT_1D_SIZE 256` with exactly 256 data rows; reject
  anything else (no resampling). Accept missing or identity `DOMAIN_MIN/MAX`,
  reject non-identity domains. Clamp values to 0..1. Rationale: the kernel
  table is fixed at 256 and all supplied files are already 256, so strict
  acceptance keeps the parser tiny and predictable. Alternative rejected:
  linear resampling of other sizes (unneeded complexity).
- D3: Replace the bool with a mode enum `OFF / ON / CUSTOM`, persisting mode
  + the existing 3 gains. Migration: old `enabled=1` becomes `ON`,
  `enabled=0` becomes `OFF`, gains preserved. Stored user gains apply only
  in CUSTOM. Rationale: "On loads the device file" is the requested semantic;
  preserving gains keeps Custom useful after upgrade.
- D4: Bundle device files at `RES_PATH/displaycal/<DEVICE>.cube` (lowercase;
  supplied files renamed on import), resolved by direct path concat from the
  `DEVICE` env var. Models without a bundled file apply the gain-derived LUT
  computed at runtime from their per-model defaults (identical to a generated
  `.cube`, but with a single source of truth and no drift risk). Rationale:
  simplest resolution; never leaves the pipe unconfigured. Alternative
  rejected: committing generated `.cube` files for unmeasured models
  (duplicates the gain defaults; the missing-file fallback is needed in code
  regardless).
- D5: Menu item "Colour correction" is a static 3-option picker
  (Off, On, Custom); R/G/B sliders stay always visible and take effect in
  Custom mode. Editing a slider while On auto-switches to Custom in the UI
  change handler (reset handlers bypass it, so reset-to-defaults is safe).
  Rationale: smallest delta from the current menu structure; keeps slider
  edits live without breaking reset ordering.
- D6: Implement once in shared code; tg5040 inherits automatically
  (`hasDisplayCal` already true); desktop/tg5050 get API-compatible updates so
  every platform still builds. Rationale: the API is already identical across
  all four `msettings`; a fork would rot.
- D7: Settings version bumps: h700 V1->V2 with an added V1 migration (copy all
  V1 fields, map enabled->mode) instead of the current reset-to-defaults;
  tg5040 V11->V12 via its existing migration style; desktop/tg5050 follow
  their own versioning. Rationale: h700 users must not lose all settings on
  upgrade.

## Recommended Approach

Extend the existing calibration stack in place rather than building a parallel
system: add a small strict 1D `.cube` parser to `displaycal.c` (exactly 256
entries, anything else rejected) behind a new
`DisplayCal_enableWithLutFile(path)` entry point; widen the persisted settings
from bool to mode+gains with versioned migration; resolve "On" to the bundled
per-model file with a runtime gain-derived fallback from per-model defaults;
swap the menu's on/off toggle for a static Off/On/Custom picker with slider
edits auto-switching On to Custom. Parse-then-apply everywhere: a file is
fully validated before its table ever touches the kernel, and any failure
keeps the last good LUT active.

## Validation Plan

- Parser harness (native, no hardware): compile `displaycal.c` with a small
  host test main; feed the 4 real files plus synthetic 256-entry files
  (comments, TITLE, missing/identity DOMAIN, trailing whitespace) and assert
  correct 256-entry output; feed non-256 sizes (e.g. 1024), short/long row
  counts, non-identity domains, non-numeric, NaN, 3D-only, and empty inputs
  and assert clean rejection with no partial state. Expected evidence:
  harness exits 0 with per-case PASS lines.
- Cross-builds: h700 `libmsettings` + `settings` via the repo toolchain
  makefiles, plus the native/desktop build to catch shared-code breakage.
  Expected evidence: clean builds, no new warnings (`-Werror` is on for
  libmsettings).
- On-device (h700): fresh boot applies stored mode; cycle Off/On/Custom and
  confirm visible change + persistence across reboot (`msettings.bin`
  round-trip, including upgrade from a V1 file with enabled=1 -> On);
  missing bundled file for the device falls back to Custom defaults with no
  error loop. The V1->V2 upgrade path is the highest-risk step.
- Manual checks that cannot be automated: visual sanity of each bundled LUT
  on its target panel; menu label/layout on small screens.

## Risks / Rollback

- Settings migration bugs could reset user settings: mitigated by explicit
  V1->V2 field copy + upgrade-path device test; rollback is reverting the
  branch since old binaries ignore unknown versions and fall back to defaults.
- Unexpected `.cube` variants: mitigated by strict parsing (reject > guess),
  bounded line reads, and a hard cap on file size; failures keep the last
  good LUT active.
- Missing bundled file for a model: defined fallback to Custom defaults, so a
  partial `.cube` set is safe to ship.
